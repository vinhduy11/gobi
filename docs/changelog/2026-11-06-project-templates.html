Project templates: message consumer and scheduled job

Specs

Add stdlib-only templates consumer and job to New Project, make the template list come from the core through a read-only project/templates control method (with the built-in list as offline fallback), and show the Service group as in the New Project mock. gRPC and cobra templates and any post-create dependency step are out of scope.

Actions

  • Core: core/internal/project/templates_worker.go (both templates), catalogue.go (Catalogue()), project/templates in daemon/control.go (entry: 1 id, 2 order, 3 group, 4 title, 5 summary, 6 available).
  • Tests: every template renders, is gofmt-clean and passes go vet and go test in a temp module; golden files in core/internal/project/testdata/templates/ (go test -update rewrites them); catalogue test; control reply test and golden bytes of one entry (Go), the same bytes decoded in Swift (NewProjectModelTests).
  • Swift: ProjectTemplate.parse and TemplateCatalog.fallback/all/use (GobiModel), ControlClient.templates(), New Project window loads and shows the core list. --selftest-newproject compares the dialog with the core list and creates and tests a consumer and a job project against a real gobid.
  • Docs: wire protocol, CHANGELOG, README, mock-gap row.

Tradeoffs

  • The decoder lives in GobiModel (like ToolStatus.parse) so it can be unit tested without a socket; ControlClient.templates() only calls it.
  • The consumer reads with several workers that share one Source, which must be safe for concurrent use; simpler than a reader goroutine plus channel, at the cost of that requirement.
  • Handler errors are logged and the worker continues; a Source error other than EOF or cancellation ends Consume with an error.
  • The workspace entry was renamed to the mock's "go.work (multi-module)" and moved to its own group, which changes the dialog order.
  • Cross-platform and ui-spec exports are deferred as instructed.
