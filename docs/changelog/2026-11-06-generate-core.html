Generate core engine (stage 4a)

Specs

Generation lives in the Go core: an item catalogue with applicability from a caret context, rendering with text/template, final text formatted with go/format, import edits through go/ast so one apply is one undo step. Control messages generate/list, generate/preview, generate/render carry a buffer version that every reply echoes. Plus a gopls code-action inventory. No UI.

Actions

  • New package core/internal/generate: nine items, import block edits (existing block, none, single line, aliased, blank), UTF-16 edit ranges, ApplyEdits, wire codec with golden bytes.
  • Daemon: generate.go dispatches the three methods; layer table lists the package as a service.
  • Tests: one exact golden per item; a temp-module test runs gofmt -l, go vet and go test; mixed-field String(); import cases; version echo.
  • Opt-in TestGoplsCodeActionInventory; results in docs/implement/generate.md.
  • Docs: wire protocol, CHANGELOG.

Tradeoffs

  • Hand-rolled import insertion over golang.org/x/tools: no new dependency, touches only the import lines; handles stdlib grouping only, third-party imports are added only to new test files.
  • Pointer receivers everywhere; the UI could pass the receiver kind later.
  • The test item creates a new _test.go and refuses if one exists, since core cannot see unsaved test buffers.
  • The mock relies on the UI sending a flattened method set.
  • Implement interface and generate test are built from our own snippets, not gopls (see the inventory).
